# v0.3.2 Desktop and Core-Module Status

## Executive status

Vel v0.3.2 is ready for **native console programs and desktop application-core projects** on the supported x86-64 targets. The compiler can tokenize, parse, type-check, emit assembly, and build the desktop example. The project manifest, source tests, host shim, packaging, and cross-platform release workflow are operational.

Vel v0.3.2 is **not yet a complete GUI desktop framework**. A production windowing toolkit, event loop, graphics backend, resource bundler, module imports, typed error values, and safe argument-vector process API remain future implementation work.

## Core module review

| Area | v0.3.2 status | Readiness |
|---|---|---|
| Tokenizer, parser, and type checker | Implemented with regression fixtures and diagnostics | Ready for current language surface |
| Strings, arrays, structs, aggregate calls | Implemented for the verified native ABI surface | Ready for supported programs; ABI is still evolving |

| `std::env` source module | Not exposed as Vel imports; C ABI foundation exists | Internal/runtime foundation only |
| `std::fs` source module | Not exposed as Vel imports; C ABI read/write/existence functions exist | Internal/runtime foundation only |
| `std::process` source module | Not exposed as Vel imports; shell-command C ABI is provisional | Do not pass untrusted input |
| `std::path`, `std::args`, `std::time`, `std::io` | Design only | Not ready |
| C and assembly integration | Assembly output and packaged C ABI header/library exist; `extern` syntax is not implemented | Manual native boundary only |
| Desktop windowing, events, graphics, and resources | Not implemented | Application-core only |

## Optimization and safety findings

The release compiler uses warnings, stack protection, fortified libc checks, and Linux full RELRO. Source loading is bounded at 64 MiB, host-shim text reads and writes use the same bound, and the arena allocator now aligns every allocation and guards capacity arithmetic. AddressSanitizer and UndefinedBehaviorSanitizer builds pass the eight-test suite. Leak detection is disabled for that profile because the frontend arena intentionally bulk-reclaims AST memory; destructor-aware cleanup remains future work.

The provisional process function still delegates to the host shell. It is suitable only for trusted, developer-controlled commands. It must be replaced with an argument-vector API before being exposed as a general-purpose Vel module.

## Desktop example readiness

`projects/desktop-app` is a verified starter project with a manifest, Vel entry point, source smoke test, asset location, and Linux/macOS and Windows helper scripts. It is suitable for experimenting with application logic and for validating the compiler’s native build pipeline. It should not be described as a GUI application until the windowing and event APIs exist.

The next desktop milestone should implement module imports and typed errors first, then a safe resource/path layer, and only then a window/event abstraction backed by platform-specific adapters. This order keeps the desktop API testable and prevents platform handles and shell behavior from leaking into the language surface.
