# Vel v0.3.2 Design: Application Foundations

**Status:** Design and implementation kickoff  
**Base release:** v0.3.1  
**Goal:** Make Vel materially more useful for real native applications without pretending that the GUI layer is already complete.

## Problem statement

Vel v0.3.1 can compile small native programs and application-core experiments, but the distribution is intentionally small because it does not yet include a standard library, multi-file project model, host APIs, or a desktop runtime. v0.3.2 should grow the platform through useful capabilities rather than by adding arbitrary package weight.

The release must preserve the current strengths: a portable C++23 compiler, explicit native targets, a small target-specific assembly layer, deterministic source validation, and honest platform claims.

## Release boundary

The v0.3.2 target is **application foundations**, not a finished GUI framework. A v0.3.2 application may be a native command-line tool, service, generator, data processor, or application core. Windowing and graphics will have a defined integration boundary, but a first-party widget toolkit is not required for this release.

### In scope

| Area | v0.3.2 outcome |
|---|---|
| Runtime ABI | Explicit metadata and contracts for strings, arrays, structs, allocation failure, and cleanup boundaries |
| Standard library boundary | A portable API surface for arguments, environment, paths, files, processes, and time |
| Project model | Manifest validation, source-root conventions, and a design-compatible path toward multi-file builds |
| Test workflow | Preserve `vel test`; add a path-aware project contract and prepare runtime assertions |
| Diagnostics | Stable source locations and structured error categories for the new project APIs |
| Desktop boundary | Define window/event/resource interfaces and an optional backend strategy without claiming GUI completeness |
| Distribution | Package the standard library/runtime support and examples in release archives when implemented |

### Explicitly deferred

- Full widget toolkit
- GPU renderer
- IDE/debugger
- ARM64 native backends
- Package registry and remote dependency resolver
- Garbage collection
- Automatic memory reclamation for arbitrary aggregates
- Production-ready cross-platform GUI application bundles

## Proposed application API

The first library surface should be small, synchronous, and testable. Names below are design targets, not available v0.3.1 syntax until implemented and covered by tests.

```vel
use std::args;
use std::env;
use std::fs;
use std::path;
use std::process;
use std::time;

fn main() {
    let root = env::current_dir();
    let config = path.join(root, "config.vel");
    if fs.exists(config) {
        print fs.read_text(config);
    }
    print process.args()[0];
}
```

The initial implementation should expose errors explicitly rather than silently returning invalid values. Until result types exist, the compiler/runtime must document the failure behavior of each function and provide a checked status path.

## Runtime ABI plan

The current three-word array header and raw NUL-terminated string pointers are useful experiments but are not sufficient as the long-term application ABI. v0.3.2 should define versioned headers:

```text
StringHeader: length, capacity, data pointer, ownership flags
ArrayHeader: length, capacity, element size, data pointer, ownership flags
Struct metadata: size, alignment, field offsets, ownership map
```

The implementation must answer these questions before nested aggregates are declared stable:

1. Who owns every allocated buffer?
2. What happens when an allocation fails?
3. How are strings and arrays copied or moved?
4. How are nested values destroyed or released?
5. Which operations are legal on immutable versus mutable values?
6. How do all three native targets report the same failure?

The first v0.3.2 implementation should prefer explicit ownership and scoped cleanup over an opaque garbage collector. Any unsupported operation must fail during checking or code generation with a clear diagnostic.

## Project model

The manifest remains intentionally small while its semantics are stabilized:

```toml
name = "my-app"
version = "0.3.2"
entry = "src/main.vel"
source = "src"
test = "tests"
```

Planned commands:

```text
vel check                 validate the project source set
vel test                  validate project tests
vel build                 build the manifest entry point
vel run                   build and execute the manifest entry point
vel doctor                report compiler and native-library capabilities
```

Multi-file compilation should be introduced only after import syntax, symbol visibility, duplicate-name diagnostics, and deterministic source ordering are specified. A manifest that merely lists files without a linker and namespace model is not sufficient.

## Desktop integration boundary

The desktop API should be layered so the compiler does not require a managed runtime:

```text
Vel application
    ↓
vel.std (filesystem, process, time, environment)
    ↓
vel.desktop (window, events, resources; optional)
    ↓
platform backend (Win32 / Cocoa / X11-or-Wayland strategy)
```

The first desktop milestone is an interface contract and one minimal backend experiment, not a promise of a complete widget library. The API must cover application lifecycle, window ownership, event polling, resource paths, and clean shutdown before controls and graphics are added.

## Implementation sequence

1. Reconcile runtime documentation and add ABI conformance fixtures.
2. Add structured diagnostic locations and stable error categories.
3. Stabilize manifest parsing and project-root discovery.
4. Add standard-library host shims behind a target-neutral interface.
5. Add one API family at a time with Linux, macOS, and Windows tests.
6. Add multi-file/import syntax only after the manifest and symbol model are specified.
7. Add a minimal desktop backend experiment and keep it feature-gated.
8. Expand release archives only when the corresponding runtime/library functionality is shipped.

## Definition of done

v0.3.2 is ready when a clean checkout can create, check, test, build, and run a documented multi-file-capable application foundation on the supported host targets; every shipped standard-library API has failure semantics and tests; the runtime ABI documentation matches the implementation; and the README clearly distinguishes application foundations from full GUI support.
