# Vel v0.3.3 Readiness Review

**Review basis:** repository `zyrndotio/Vel`, current `main` branch

**Purpose:** distinguish capabilities that are implemented and tested from capabilities that are documented but still missing, while moving the active release target to v0.3.3.

## Executive assessment

The repository is a usable **v0.3.2 application-foundation compiler**, not yet a complete desktop GUI platform. The compiler frontend, project commands, native x86-64 assembly paths, scalar-array and string runtime foundations, host-shim library, sample projects, release packaging workflow, and security hardening are present in the source tree. The release documentation is also unusually explicit about the remaining boundary.

The primary v0.3.3 work is therefore not a cosmetic version bump. The project needs a coordinated release contract, a reproducible validation environment, and completion of the highest-priority foundations that the v0.3.2 documents still mark as unfinished. A first v0.3.3 release should not claim features that are only design documents.

## What is present

| Area | Evidence in repository | Assessment |
|---|---|---|
| Compiler frontend | `src/tokenizer.hpp`, `src/parser.hpp`, `src/type_checker.hpp`, `src/ast.hpp` | Present for the documented language surface. |
| Native code generation | `src/codegen.hpp` and target handling in `src/main.cpp` | Present for Linux, macOS, and Windows x86-64 assembly paths. |
| Project CLI | `vel check`, `build`, `run`, `test`, `clean`, `doctor`, and manifest handling in `src/main.cpp` | Present and covered by shell fixtures. |
| Strings and scalar arrays | Runtime/code-generation implementation plus data-type tests | Present for the verified subset; not a complete recursive aggregate ABI. |
| Host runtime shim | `runtime/vel_std.h` and `runtime/vel_std.cpp` | Present for environment, file, and provisional process operations. |
| Packaging | CPack metadata, Inno Setup script, and release workflow | Present for the existing artifacts. |
| Release CI | `.github/workflows/ci.yml` and `.github/workflows/release.yml` | Present, but local validation cannot run in the current sandbox because CMake and a C++ compiler are unavailable. |
| Sample projects | `projects/console` and `projects/desktop-app` | Present; the desktop sample is an application-core example, not a GUI app. |
| Security hardening | Bounded source/runtime I/O, hardened compiler flags, sanitizer option, signing hooks | Present in the documented scope, subject to CI verification. |

## What is missing

| Area | Current gap | v0.3.3 consequence |
|---|---|---|
| Versioned ABI | The design calls for explicit string/array headers, struct metadata, ownership flags, and cleanup rules, but the status document says recursive layout and ownership remain unfinished. | Release-blocking if v0.3.3 intends to promise ABI stability. |
| Vel-level standard library | `std::args`, `std::env`, `std::fs`, `std::path`, `std::process`, `std::time`, and `std::io` are not exposed through imports. | Must remain documented as runtime foundations only, or be implemented before claiming availability. |
| Safe process API | The process shim delegates to the host shell and is explicitly unsafe for untrusted input. | Do not expose as a general-purpose standard-library API. |
| Module/import system | No `use` syntax, namespace resolution, visibility model, or multi-file linker model is implemented. | Blocks a genuine multi-file standard-library release. |
| Structured diagnostics | Source locations, stable error categories, snippets, and actionable hints are still roadmap items. | Needed for a polished v0.3.3 developer experience. |
| Recursive aggregate ownership | Nested aggregate copy/move/destroy semantics are not complete. | Must remain experimental until conformance fixtures exist. |
| Desktop APIs | No stable window, event, graphics, or resource API; no native application bundle workflow. | v0.3.3 must not be marketed as a GUI framework. |
| Resource bundling | No implemented resource loader or platform bundle integration. | Missing for turnkey desktop distribution. |
| Tooling | Formatter, language server, debugger, package manager, dependency resolver, and documentation generator are absent. | Deferred ecosystem work, not v0.3.3 core requirements unless explicitly chosen. |
| Update security | Production certificate/provider, signed manifest, digest verification before install, atomic replacement, rollback, and channels are not complete. | Release update path remains incomplete for production use. |
| Cross-platform release validation | Local Linux build and tests pass, but macOS and Windows release jobs still need to validate the tagged artifacts. | CI must pass on all supported x86-64 targets before tagging v0.3.3. |

## Recommended v0.3.3 scope

A defensible v0.3.3 should be a **foundations and correctness release**. It should stabilize the manifest and project-root behavior, add structured diagnostics, define and test the versioned runtime ABI, and provide ABI conformance fixtures on all supported targets. It should either implement a safe argument-vector process API or keep process execution explicitly internal and provisional. It should not claim GUI completeness, modules, a package registry, ARM64 targets, or production application bundles unless those features are separately implemented and tested.

The minimum release gate is a clean checkout that can configure, build, run the complete test suite, validate the sample projects, and produce version-matched artifacts from a `v0.3.3` tag on Linux, macOS, and Windows x86-64. The release notes, README badge, installer metadata, project template version, compiler version string, and package names must all agree on `0.3.3`.

## Validation note

The initial local validation was blocked because the sandbox did not have CMake or a C++ compiler. After provisioning CMake, GNU C++, and NASM, the project configured and built successfully with `VEL_VERSION=0.3.3`. The complete eight-entry CTest suite then passed, including the runtime smoke test after correcting the oversized-write validation order. The remaining release gate is cross-platform validation through the Linux, macOS, and Windows CI jobs.

## Conclusion

The repository is **not missing the core v0.3.2 application-foundation implementation**, but it is missing several items needed to call v0.3.3 a stable application-platform release. The safest change is to make v0.3.3 an explicit readiness target, keep historical v0.3.2 documents intact, update active version metadata consistently, and use the missing-feature matrix above as the release checklist.
